# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)

Спроектирован базовый процесс разработки микросервиса «Расчет корзины и скидок»: создан публичный репозиторий, заданы правила ветвления и CODEOWNERS, настроена проверка flake8 в GitHub Actions, разобран legacy-алгоритм и подготовлены артефакты для code review. Для хранения истории транзакций и баллов рекомендуется PostgreSQL из-за транзакционной целостности и развитых средств запросов.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

Оценка по шкале 1–5 (5 — лучше). Вес каждого критерия отражает значимость хранения финансовых операций; сумма весов равна 1.00.

| Критерий | Вес | PostgreSQL | MongoDB |
|---|---:|---:|---:|
| ACID и целостность транзакций | 0.35 | 5 | 4 |
| Финансовая согласованность и ограничения данных | 0.25 | 5 | 3 |
| Аналитические запросы и отчетность | 0.15 | 5 | 3 |
| Гибкость схемы промокодов | 0.10 | 4 | 5 |
| Экосистема и стоимость эксплуатации | 0.15 | 5 | 4 |
| **Итого** | **1.00** |  |  |

### 2.2. Расчет и обоснование выбора

Взвешенная оценка = сумма (вес критерия × балл СУБД).

- PostgreSQL = 0.35×5 + 0.25×5 + 0.15×5 + 0.10×4 + 0.15×5 = **4.90**.
- MongoDB = 0.35×4 + 0.25×3 + 0.15×3 + 0.10×5 + 0.15×4 = **3.70**.

Победитель — PostgreSQL: для истории транзакций и баллов важнее согласованность, ограничения целостности и транзакции, чем максимальная гибкость схемы.

## 4. Инструментальный контроль качества

### 4.1. Настройка CI/CD

Пайплайн: [.github/workflows/qa.yml](.github/workflows/qa.yml); конфигурация flake8 в [.flake8](.flake8). Проверка запускается при PR в `develop`.

### 4.2. Работа Quality Gate

В [PR #2](https://github.com/LegendaryGrib/lab1-comprehensive-grachev/pull/2) коммит `test: add code with intentional errors` намеренно содержал неиспользуемый `import os` и строку длиннее 80 символов; первый запуск линтера завершился ошибкой. Затем коммит `fix: resolve linter errors` удалил неиспользуемый импорт и чрезмерно длинную строку. Проверка повторно завершилась успешно; в истории PR видны оба статуса и исправление. PR слит в `develop`.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

![Диаграмма деятельности расчета скидок](https://raw.githubusercontent.com/LegendaryGrib/lab1-comprehensive-grachev/feature/review-plan/docs/uml_diagram.png)

Диаграмма показывает старт и завершение, базовую скидку при `cart_sum > 15000`, перебор промокодов с проверками `SUMMER` и `VIP`, скидку уровня и ограничение цены в 70% от исходной суммы.

Выявленные Code Smells: магические числа (15000, 0.85, 500, 0.90, ставки уровней и 0.70); функция смешивает применение базовой скидки, промокодов, tier и ограничение цены; порядок промокодов и уровней влияет на результат; нет проверки входных данных; поведение неизвестных и повторных промокодов не определено; денежные значения рассчитываются обычной арифметикой с плавающей точкой без явного округления.

### 5.2. План code-review

План: [docs/review-plan.md](https://github.com/LegendaryGrib/lab1-comprehensive-grachev/blob/feature/review-plan/docs/review-plan.md). В нем заданы цели по точности и антифроду, проверяемые критерии (валидация, отсутствие магических чисел, покрытие выше 80%), участники с ролями и пошаговая эскалация разногласий. PR с планом и UML оставлен открытым: [#3](https://github.com/LegendaryGrib/lab1-comprehensive-grachev/pull/3).

## 6. Заключение

Защита ветки и обязательный PR создают проверяемый процесс изменений, CODEOWNERS определяет ответственность, а автоматический линтер обнаруживает часть ошибок до слияния. Решение PostgreSQL снижает риск нарушения финансовой целостности; формализованный review plan задает контроль алгоритмов скидок, валидации и тестового покрытия.
